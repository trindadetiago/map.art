Solid decisions

decided

Worker is separate from the API

Vercel kills long requests. Heavy work runs in its own process.

Vercel function timeouts are 10–300s by tier — they'll kill any real generation. A long-running worker on Fly/Railway/Render/VPS is the only sane place. Backend stays thin: auth, enqueue, presign.

decided

Postgres is the queue

One DB for state + jobs. No Redis on day 1.

SELECT … FOR UPDATE SKIP LOCKED is the standard pattern. Use graphile-worker or pgmq instead of reinventing leasing / retries / visibility.

decided

Only the worker writes blob

Backend just presigns read URLs.

Saves egress, simpler IAM, single writer. Backend never touches images directly.

decided #6

Two worker pools, not one

Render is RAM-heavy; stylize is a thin GPU caller. Split them.

One pool means provisioning for the worst case of both. Split = independent autoscaling triggers, cheaper at idle.

decided

Our model behind a stable HTTP contract

We own the weights + the endpoint. Where it's hosted can change anytime.

Train Qwen Image-Edit LoRA on python/training/v01. Wrap in a small HTTP service: POST /edit { image, mask?, prompt, steps, seed } → png.

That contract is the abstraction boundary. Replicate / Modal / our own H100 — caller doesn't know. Lets us run v01 and v02 side-by-side for A/B.

Difficulties & open questions

hardest problem

Server-side render may not be feasible cleanly

Three.js + Google 3D Tiles in a headless container is the goal. If it's too painful, render stays in the user's browser.

Options, in priority order:

  1. Headless Chromium (Playwright) running the same Three.js scene. Heavy (~500MB–1GB/worker, SwiftShader for CPU WebGL), but plausible.
  2. headless-gl / gl in Node. Flaky, partial WebGL parity.
  3. Rewrite off the browser stack (wgpu / Blender headless). Cleanest, biggest scope.

Plan B: keep render client-side. Browser uploads rendered tile to backend, backend writes to blob + enqueues stylize. Worse UX (tab has to stay open) but unblocks the rest.

scheduling

Stylize is a DAG, not a queue

A tile can only run once its neighbors are done. Andy says this part is "irreducibly complex."

Two implementations:

  • depends_on UUID[] per job; worker only claims when all deps are done.
  • Planner job that emits the current wavefront, re-runs after each batch.

Don't promise full automation in v1.

scope

Eager render, lazy stylize

Render the whole area up-front (cheap, parallel). Stylize only what the user asks for (expensive).

Render jobs are independent — kick them off the moment the user confirms area. Stylize costs real $$ per call; never burn it on tiles no one will see.

scale

Jobs table will explode

Hundreds of thousands of rows per project. Plan partitioning + cleanup now.

  • Soft-delete or partition completed jobs after N days.
  • Partition by project_id once multi-tenant.
  • Never store image bytes in Postgres — only blob keys.
cost decision

Where does our model service run?

Biggest cost lever in the whole SaaS. Start serverless GPU, move self-hosted later.

  • oxen.ai hosted — convenient, $$/call, slow.
  • Serverless GPU (Replicate / Modal) — pay per second, scales to 0, cold starts. Start here.
  • Self-hosted H100 / L40S — cheapest at volume, real ops.
our model

The model service is something we build

Base Qwen + our LoRA + small HTTP wrapper, all in one container we deploy anywhere.

  • Base: Qwen/Image-Edit (open weights).
  • Our LoRA: trained on python/training/v01 (~1,696 augmented examples). Trigger: <mapart isometric pixel art>.
  • Container: weights + LoRA + FastAPI. Same image on Replicate, Modal, or our VM.
  • Versioning: LoRA artifacts in blob (/models/v01.safetensors).
  • Provider abstraction: add mapart to packages/models next to nano-banana / openai.

Once we own weights + contract, we control the cost curve and can ship new model versions without touching anything else.

Things missing from the diagram (SaaS basics)

must-have

Auth + multi-tenancy

Every query scoped by user/org. RLS or strict app filters.

Project ownership on every blob path. Postgres row-level security is the safest default.

must-have

Quota check before enqueue

Decrement credits at enqueue, not after the worker spends.

Reserve credits when the job is created, refund on failure. Otherwise concurrent requests can blow past quota and we eat the cost.

must-have

Idempotency on every job

Workers retry — a retry must not double-charge or double-write.

idempotency_key on the job row. Pass a stable request id to the inference service too.

UX

Two priority lanes from day 1

bulk vs interactive. Otherwise edits wait behind 5,000 jobs.

Just a priority INT on the jobs table is enough.

ops

Autoscaling has a ceiling

Stylize parallelism is capped by wavefront width, not queue length.

If only 6 tiles are dependency-ready, spinning up 50 workers is pure burn. Track ready jobs, not pending.

observability

Per-job cost + timing stamp

Log model id, duration, $-estimate, neighbor composition on every job.

Without this we can't debug seams, can't detect model regressions, and can't price the product.

Sketch — jobs table

create table jobs (
  id              uuid primary key,
  project_id      uuid not null,
  type            text not null,          -- 'render' | 'stylize'
  x               int  not null,
  y               int  not null,
  priority        int  not null default 100,  -- lower = sooner
  status          text not null default 'pending',
                  -- pending | ready | running | done | failed | cancelled
  depends_on      uuid[] not null default '{}',
  idempotency_key text unique,
  attempts        int  not null default 0,
  last_error      text,
  output_blob_key text,
  cost_cents      int,
  duration_ms     int,
  locked_by       text,
  locked_until    timestamptz,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);

create index jobs_ready_idx
  on jobs (priority, created_at)
  where status = 'ready';

create index jobs_project_idx on jobs (project_id, status);

The two decisions to nail first

decision #1

Can render run server-side?

Spike Playwright + Google 3D Tiles in a container. If it renders cleanly, ship it. If not, fall back to client.

Target: single tile in <30s. Don't commit the rest of the architecture to a path we haven't proven.

decision #2

Where does our model service live?

Spike Replicate + Modal with a tiny LoRA. Measure cold-start, $/call, p50/p99.

That's the per-tile floor cost of the SaaS — every other number is a multiplier on it.
