map.art — architecture

Three services, one Postgres, one blob store. The tiles table is both the data and the job queue — workers poll it, claim rows with SKIP LOCKED, and never speak HTTP to anything. This is the shape we're building toward.

The three services

service

web

Next.js. The only thing that speaks HTTP. UI + a thin API.

User picks an area; web computes the grid, then inserts one tiles row per cell (all render / pending) plus the project row. After that web only reads tile state to show progress and serves the finished images.

web does no rendering and no generation — it never blocks on heavy work.

service

worker-render

Headless Chromium + Three.js. Turns (lat, lng) into a raw render PNG.

Polls for render / pending tiles, claims one, renders it, writes the PNG to storage, then writes rendered_img_path and flips status = done. No HTTP in, no HTTP out — just Postgres and storage.

service · planned

worker-stylize

Calls the image-edit model. Turns a rendered tile + its neighbors into pixel-art.

Polls for tiles that have finished rendering and whose neighbors have all rendered too, claims one, stylizes it using the neighbor tiles as context, writes stylized_img_path, flips current_status_type = stylize and status = done.

The generation itself goes through @mapart/models — the worker doesn't care which model is behind it.

The load-bearing rule: workers talk to Postgres and blob storage, nothing else. No worker calls web, and web never calls a worker. All coordination happens through rows in the tiles table. That's what lets us scale each worker pool independently and run them anywhere.

The two tables

project

create table project (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  description text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

Just a grouping + label. Everything operational lives on tiles. Progress (“42 of 900 done”) is a group by status over tiles — not stored, never out of sync.

tiles — the core

create table tiles (
  id                  uuid primary key default gen_random_uuid(),
  project_id          uuid not null references project(id),
  x                   int  not null,            -- grid column
  y                   int  not null,            -- grid row
  lat                 double precision not null,
  lng                 double precision not null,
  current_status_type text not null default 'render',
                      -- 'render' | 'stylize'
  status              text not null default 'pending',
                      -- pending|progress|done|error
  retry_attempt       int  not null default 0,  -- 0..3 per phase
  neighbors           uuid[] not null default '{}', -- ≤ 8
  rendered_img_path   text,
  stylized_img_path   text,
  created_at          timestamptz not null default now(),
  updated_at          timestamptz not null default now(),
  unique (project_id, x, y)
);

One row, two lives

current_status_type flips render → stylize; status cycles within each phase. A single row carries a tile from raw render all the way to finished pixel-art.

x / y / lat / lng

x, y are the tile's index in the precomputed grid; lat, lng are its real-world center. web computes all four at insert time from the chosen area using @mapart/geo tile math + the hardcoded render params.

neighbors

A list of adjacent tile ids — up to 8 (the diagonals count), fewer on edges and corners. Precomputed at insert time so the stylize gate is one cheap query, not a geometry calculation per poll.

the two paths

rendered_img_path and stylized_img_path are blob keys, never image bytes. A non-null rendered_img_path is also the durable signal that “render finished here” — see the neighbor rule below.

Lifecycle of a tile

  1. web

    Project created → grid exploded into rows

    User picks an area. web inserts the project and one tiles row per grid cell, each with its x, y, lat, lng and precomputed neighbors, all at render / pending.

  2. worker-render

    Claim a pending render

    Polls for render / pending, atomically claims one row with FOR UPDATE SKIP LOCKED, flips it to progress, commits. The lock is released the instant it commits — it does not hold a row lock during the render.

  3. worker-render

    Render → store → mark done

    Renders (lat, lng) to a PNG, writes it to storage, then updates the row with rendered_img_path and status = done. On failure it bumps retry_attempt instead (see retries).

  4. worker-stylize

    Find a render-done tile whose neighbors are all rendered

    Polls for render / done tiles where every neighbor already has an image path — one query, no exceptions. If even one neighbor hasn't rendered yet, the tile waits.

  5. worker-stylize

    Claim, promote to the stylize phase

    Claims the tile with SKIP LOCKED and promotes it: current_status_type = stylize, status = progress, retry_attempt = 0. (Retries reset per phase.)

  6. worker-stylize

    Stylize with neighbor context → store → done

    Reads the tile's render plus its neighbors' images from storage, generates the stylized tile through @mapart/models, writes the PNG, then sets stylized_img_path and status = done. Terminal state.

How the queue works

claiming

SKIP LOCKED = safe concurrent claim

Many worker instances poll the same table. The claim transaction locks one row and skips any row another worker already holds — no two workers ever grab the same tile.

The whole trick: FOR UPDATE locks the rows a SELECT returns; SKIP LOCKED tells Postgres to step over rows someone else has locked instead of waiting. Three workers hitting it at once get three different tiles, with no central coordinator.

lock lifetime

The lock is held for milliseconds, not the whole job

Lock → flip status = progress → commit. After commit the row is protected by state, not by a lock — the next poll skips it because it's no longer pending.

Holding a row lock for a 30-second render would serialize everything and defeat the point. Instead the transaction is tiny: claim and mark progress, commit, then do the slow work outside any transaction.

polling

Adaptive polling

Idle workers poll every ~30s. When a poll returns a tile, poll again immediately — drain the backlog fast, idle cheaply when there's nothing to do.

retries

retry_attempt 0 → 3, then error

On failure, bump retry_attempt and drop back to pending. At the 4th failure (retry_attempt = 3 and it fails again) set status = error.

Workers only ever pick up pending. error is a dead end — never auto-retried, surfaced for a human. The counter is per phase: promoting a tile from render to stylize resets retry_attempt to 0, so render failures don't eat into the stylize budget.

Claim queries

-- worker-render: grab the next pending render
begin;
  select id from tiles
  where current_status_type = 'render' and status = 'pending'
  order by id limit 1
  for update skip locked;
  -- then, for the returned id:
  update tiles set status = 'progress', updated_at = now() where id = $1;
commit;  -- lock released here; render happens after, outside the txn

-- worker-stylize: a render-done tile whose neighbors have ALL rendered
begin;
  select t.id from tiles t
  where t.current_status_type = 'render' and t.status = 'done'
    and not exists (
      select 1 from tiles n
      where n.id = any(t.neighbors)
        and n.rendered_img_path is null   -- a neighbor not yet rendered
    )
  order by t.id limit 1
  for update skip locked;
  -- then promote the returned id into the stylize phase:
  update tiles
    set current_status_type = 'stylize', status = 'progress',
        retry_attempt = 0, updated_at = now()
    where id = $1;
commit;
the rule that matters

Neighbor readiness keys on the image path, not the phase

Gate stylize on rendered_img_path IS NOT NULL for every neighbor — never on current_status_type = 'render'.

If the gate checked the phase column, the first tile to get stylized would flip to stylize and then fail its neighbors' readiness checks forever — they'd never stylize. Starvation.

rendered_img_path is set once and never cleared, so it stays a true “render finished here” signal regardless of what phase the neighbor later moves to. (A stylized neighbor has both paths set, so checking the rendered path alone is enough — it's equivalent to “has at least one image path”.)

Out of scope for now

later

Cancel

No canceled state yet — nothing cancels a tile today. If/when we add project cancellation, it becomes a status that the claim queries exclude.
