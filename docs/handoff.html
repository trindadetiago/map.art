Wiring

New apps/worker-stylize package, a dev:worker-stylize script in root package.json, and a tab in mprocs.yaml so it runs alongside the others under pnpm dev.

The render consumer is the template. Its shape — claim one row, do the slow work outside any transaction, mark done or retry, back off when idle — is exactly what the stylize consumer needs: 

// the loop already written for render — stylize is the same skeleton
const tile = await claimNextStylize();      // SKIP LOCKED + neighbor gate
if (!tile) { await idle(); continue; }   // empty queue → back off ~30s

const render = await getStorage().get(tile.renderedImgPath);
const neighbors = await readNeighborImages(tile.neighbors);  // the context strips
const { image } = await model.generate({ input: composite, prompt });
await getStorage().put(stylizeKey(tile), image);
await completeStylize(tile.id, stylizeKey(tile));   // or failOrRetry(tile.id)

Two things to know before building it

  1. Learn the algorithm first — it's already implemented in Python

    Do not invent the stylize logic. The real algorithm — how a rendered tile is combined with its already-stylized neighbours into the model's input, and how the result is cropped back out — lives in python/algorithm_playground.py ("Algorithm A"). Read it; the TypeScript worker should port that same recipe.

    The shape of it, from that file:

    • Expanding-radius order. Tiles aren't stylized arbitrarily — they walk out from a corner: (0,0) → (0,1)(1,0) → (0,2)(1,1)(2,0) → … so each new tile already has stylized neighbours to anchor on. (In production this order is what the neighbors-readiness gate in claimNextStylize approximates.)
    • Composite input. Each model call is one 1024×1024 image: the center ~80% is the raw render to stylize; each side that has a stylized N/S/E/W neighbour gets a ~10% strip cropped from that neighbour's adjacent edge. A missing neighbour (grid edge) → use the opposite side at 20% to keep it square. Diagonals are deliberately skipped.
    • Red-box convention. A 1px red rectangle marks the central region to fill — the same convention the LoRA was trained on. The prompt asks the model to fill the outline and remove the border.
    • Extract. After inference, crop the outlined region back out and resize to 1024×1024 — that's the stylized tile that gets stored and becomes a neighbour for the next step.

    The Python version targets a 3×3 grid and an Oxen-hosted inference endpoint; the worker generalizes it to an arbitrary grid driven by the tiles queue, calling the model through @mapart/models instead. The composite recipe and ordering logic are the part to copy faithfully.

  2. You can test it with a stub model — but a real run would prove more

    The worker talks to the model only through the ModelClient interface (packages/models/src/types.ts): generate({ input, prompt }) → { image, metadata }. That means the whole pipeline can be exercised with a stub model that ignores the prompt and just returns something — e.g. echo the input back, or paint a flat colour — so you can verify claiming, neighbour reads, compositing, storage writes, retries, and the phase flip end-to-end without any GPU, API key, or cost.

    That's enough to prove the plumbing is correct. But it would be valuable to also run at least one project through a real stylize pass — even a single small grid — so we can see an actual stylized result come out the other end and confirm the algorithm port (composites, strips, crop) matches what the Python playground produces. Plumbing-green and "it actually makes pixel-art" are two different signals; aim to land both.

Suggested order of work

  1. Read python/algorithm_playground.py end to end. Understand the composite + ordering.
  2. Scaffold apps/worker-stylize off the worker-render consumer skeleton.
  3. Port the composite/strip/crop logic to TS (a pure helper, ideally testable in isolation).
  4. Wire a stub ModelClient and run a project through to confirm the plumbing.
  5. Swap in the real model and run one small grid to confirm the output looks right.
  6. Add the mprocs.yaml tab + dev:worker-stylize script.

Don't forget the conventions

Per CLAUDE.md: business logic that isn't UI belongs in packages/* (server-only, no React); the worker is an apps/* service. Read process.env only through @mapart/env. Always go through getStorage(). Type-check with pnpm exec tsc --noEmit after non-trivial changes — there are no tests yet, so tsc is the correctness signal.
