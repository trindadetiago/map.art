How isometric.nyc renders its viewer

A reference teardown of cannoneyed/isometric-nyc's public map viewer, kept here because its shape is the one map.art will likely adopt for shipping a zoomable final map. The punchline: the runtime viewer is not 3D. The isometric pixel-art is baked into a single enormous flat image ahead of time, sliced into a deep-zoom tile pyramid, and served to a dumb-but-fast 2D pan/zoom widget.

One sentence: Three.js renders source frames offline → a generative model stylizes them → the stitched mega-image is exported to a DZI/WebP pyramid with libvips → OpenSeadragon pans/zooms it with pixel smoothing turned off → static tiles sit on Cloudflare R2 behind a thin caching Worker.

Two "visualizers", don't confuse them

build-time · not shipped

The Three.js renderer (src/web)

Referenced in the README as the "3D map tiles data viewer / renderer (Three.js)". It produces the aerial/isometric source frames that get fed to the generative model. It was not included in the open-sourced tree — only src/app, src/isometric_nyc, and src/demos shipped.

This is the direct analog of our @mapart/renderer <Scene> + apps/worker-render.

runtime · the public site

The OpenSeadragon viewer (src/app)

What people actually see at isometric.nyc. A React + Vite + Bun single-page app whose entire job is to pan and zoom a pre-rendered pixel-art image served as tiles. This doc is about this one.

The analog for us would be a new viewer route/app consuming our stitched stylized output.

The stack

React + TypeScript Vite (build) Bun (pkg mgr) OpenSeadragon (tile viewer) DZI / WebP (tile format) libvips · dzsave (export) Cloudflare R2 (hosting) Cloudflare Worker (cache + CORS)

The core insight

The "3D" / isometric look is baked into the pixels by the offline generation pipeline. At runtime there is no scene, no camera, no Three.js — just a flat raster that happens to look isometric. That means the viewer can be the cheapest, sharpest thing possible: a 2D deep-zoom image widget. Everything below follows from that decision.

Pipeline, end to end

  1. build · python

    Stitch + export the mega-image to a DZI pyramid

    src/isometric_nyc/generation/export_dzi.py drives libvips (dzsave) to slice the full-resolution stitched map (>100k px wide) into a pyramid of 512 px WebP tiles. WebP buys ~25–35% over PNG; libvips is used because it streams huge images without loading them whole.

    Optional flags: --png, --bounds v1.json (clip to the NYC outline), --no-postprocess, --dry-run.

    tiles.dzi              # DZI descriptor (XML)
tiles_metadata.json    # grid dims, origin, tileSize, appDefaults (start pos/zoom)
tiles_files/
  9/0_0.webp           # lowest zoom level
  ...
  17/0_1.webp          # full-res tiles, 512px WebP
  2. serve · cloudflare

    Push tiles to R2, front them with a tiny Worker

    Tiles live on Cloudflare R2. worker/src/index.ts is a ~60-line Worker that proxies R2 and does two things only: stamp Cache-Control: public, max-age=31536000, immutable and add CORS. It checks the Cloudflare edge cache first (caches.default) before touching the bucket. No tile logic lives here.

  3. client · react

    Boot from metadata, not the image

    App.tsx fetches tiles_metadata.json (falling back to a legacy manifest.json) to learn gridWidth/gridHeight/tileSize/origin and computes totalWidth = gridWidth × tileSize. It restores the last view from localStorage, or uses appDefaults (a default start position + zoom written by the exporter). config.ts resolves which dataset/CDN to hit via env (USE_R2_NYC) or URL params (?export=, ?r2=true, ?debug=true, ?reset=1).

  4. client · openseadragon

    One OpenSeadragon viewer does the rest

    IsometricMap.tsx is the whole viewer: it instantiates a single OpenSeadragon instance with a custom tile source, wires pan/zoom/hover, and overlays cosmetic effects. Details below.

Inside IsometricMap.tsx — the clever bits

level remapping

Mapping OSD levels → on-disk folders

OpenSeadragon derives its own pyramid level numbers from image dimensions (maxLevel = ceil(log2(maxDim)) ≈ 17; minLevel = ceil(log2(tileSize)) = 9 for 512px). The exporter numbered folders 0..8. So getTileUrl subtracts the offset:

const fileLevel = level - osdMinLevel;
const dziBase = dziUrl.replace(".dzi", "_files");
return `${dziBase}/${fileLevel}/${x}_${y}.webp`;
pixel art

Keeping pixels crisp, not blurry

This is what makes pixel-art survive a zoom widget:

  • imageSmoothingEnabled: false — no bilinear blur
  • maxZoomPixelRatio: 1 — never upscale past 1 image-px = 1 screen-px
  • subPixelRoundingForTransparency: 1 — round tile positions to kill shimmer while panning
  • smoothTileEdgesMinZoom: 1.0 — only soften edges when zoomed out past 1:1
coordinate systems

World coords ↔ OSD coords

The app's own ViewState is { target: [worldX, worldY], zoom: log2scale } with Y-up. OSD uses normalized 0..1 coords with Y-down. worldToOsd / osdToWorld convert both ways (note the 1 - y flips and the log2 zoom conversion against window.innerWidth).

gotcha

Breaking the feedback loop

React state drives OSD, and OSD's viewport-change drives React state — a loop. Two refs guard it: isUpdatingFromProps (set while pushing state into OSD) and lastOSDViewState (so the sync effect can skip values that originated from OSD itself, within an epsilon).

free features

Minimap + hover from OSD

The minimap is OSD's built-in navigator (top-right, navigatorSizeRatio: 0.15). Tile hover is just viewportToImageCoordinates then floor(x / tileSize), bounds-checked against the grid.

cosmetics (DOM/CSS)

CRT overlays, not in the tiles

ScanlineOverlay is a pure CSS repeating-linear-gradient + a radial mask for CRT vignette. WaterShaderOverlay (shaders/water.ts) is a WebGL effect, but it's gated behind ?debug=true and disabled in production (it needs individual tile files, not the flattened DZI).

Why DZI + OpenSeadragon (vs. rolling your own)

ChoiceWhy
DZI (Deep Zoom Image)OpenSeadragon's native format → near-zero custom tile-loading code. Just an XML descriptor + a folder pyramid. Works on any static file server / CDN.
WebP tiles25–35% smaller than PNG; browser handles caching/prefetch natively.
libvips dzsaveGenerates the whole pyramid in one streamed pass over a >100k-px image without exhausting memory.
OpenSeadragonMature pan/zoom, built-in navigator/minimap, gesture handling, tile prefetch, placeholder fills — all configurable, smoothing toggleable for pixel art.
R2 + WorkerStatic immutable tiles + edge cache = cheap and fast at scale. The Worker only adds headers; no app logic on the hot path.

What this means for map.art

Their architecture splits exactly like ours. A build-time Three.js render stage (produce source images) → a generative stylize stage → and then a separate, deliberately-dumb 2D pyramid viewer for the final product. The Three.js piece is offline-only, just like our @mapart/renderer + apps/worker-render.

When we're ready to ship a zoomable final map, the cheapest sharp path is the same recipe:

  1. Stitch our stylized tile outputs into one large raster.
  2. libvips dzsave → DZI/WebP pyramid (+ a small metadata.json with grid dims, origin, and default view).
  3. Serve tiles from our storage/CDN (we already have @mapart/storage on S3/MinIO → AWS).
  4. A thin viewer (an apps/web route, or a dedicated app) mounting OpenSeadragon with imageSmoothingEnabled: false and maxZoomPixelRatio: 1.

A natural home in our monorepo: a packages/export for the pyramid generation (server-only, no React — fits the package boundary) and a viewer route in apps/web. The OpenSeadragon component itself is UI, so it lives in an app, never a package.
