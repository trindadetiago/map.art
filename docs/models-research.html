Mudança de foco desde 17/mai. A pergunta não é mais "qual modelo chinês é mais barato pra chamar via API?" — agora é "qual o melhor base model pra fazer LoRA, e onde rodar o serviço?". Custo passa a ser per-image servido (base + LoRA hot-swap) ao invés de list price de endpoint pronto.

Recomendação consolidada:

  1. Treinar v01.safetensors em cima de Qwen-Image-Edit-2511 via fal.ai trainer.
  2. Servir via fal-ai/qwen-image-edit-plus-lora passando loras: [{path}] — zero ops, $0.03/MP.
  3. Migrar pra Modal H100 quando volume passar ~50k imgs/mês (5× mais barato a quente).
  4. Manter Z-Image-Turbo como tier "cheap" pra restyle sem máscara — $0.005/MP é o piso absoluto.
  5. Planejar migração pra Qwen-Image-2.0 Q3/2026 — 3× mais barato pra self-host, beats FLUX em benchmarks, fal já tem trainer compatível.

Contexto do produto

Calibração necessária pra ler a pesquisa. Tudo abaixo é do architecture.html (commit c3be71b arc) sincronizado com o estado de origin/main.

pipeline

Mesmo contrato de generate

PNG do tile + prompt + máscara opcional → PNG editado. Continua o GenerateParams de packages/models/src/types.ts: 

interface GenerateParams {
  input: Buffer;       // PNG do tile
  prompt: string;
  reference?: Buffer;
  mask?: Buffer;       // inpaint opcional
  seed?: number;
}
direção SaaS

Modelo atrás de HTTP estável

Worker 1 (render) → Worker 2 (stylize, orquestra) → nosso serviço de modelo via POST /edit { image, mask?, prompt, seed } → png. Onde o serviço roda muda — o contrato não.

Postgres como queue (graphile-worker). Blob storage (S3/R2/GCS).

dataset

v01 — JP isométrico

python/training/v01/ — 1696 exemplos (106 pairs × 8 mask variants × 2 flips). Subido pro oxen.ai como trindadetiago/mapart-isometric-v01.

Trigger phrase: <mapart isometric pixel art>.

hosting plan

v1 fal/Replicate · later self-host

Architecture.html lista "v1: Replicate / Modal" e "later: self-host H100". Esta pesquisa refina: fal.ai supera Replicate pra início (endpoint c/ LoRA pronto). Modal vira a migração natural quando volume justificar.

recomendação

Por que fal.ai é a jogada inicial

  • Tem qwen-image-edit-plus-lora com parâmetro loras: [{path: <URL ou HF repo>, scale}] — exatamente a interface que o serviço precisa.
  • Tem qwen-image-edit-2511-trainer — vocês treinam e servem na mesma plataforma.
  • Zero infra própria — adia toda a complexidade de "model service container" pra quando importar.
  • Cold start managed — desaparece como problema.
  • $0.03/MP é só ~10% mais caro que o piso teórico (Modal), mas economiza 100% do trabalho de operar GPU.
próximo passo

Quando trocar pra Modal

Quando volume passar ~50k imgs/mês ($1.500/mês na fal vs ~$300/mês no Modal), a economia paga o esforço de:

  • Bundle do base model (20B) na imagem Docker
  • LoRA hot-swap a partir de Modal Volume ou HF
  • @app.cls(container_idle_timeout=...) + keep_warm=N pra cortar cold start
@app.cls(gpu="H100", container_idle_timeout=300, keep_warm=1)
class QwenEditService:
    @modal.enter()
    def load_base(self):
        self.pipe = QwenImageEditPipeline.from_pretrained(
            "Qwen/Qwen-Image-Edit-2511")

    @modal.method()
    def edit(self, image_b64, mask_b64, prompt, lora_url, seed):
        lora_path = download_lora(lora_url)  # cached on Volume
        self.pipe.load_lora_weights(lora_path)

Plano de implementação

0

Treinar v01 LoRA na fal (1-2 dias, ~$4)

Empacotar dataset em formato qwen-image-edit-2511-trainer aceita ({input, target, prompt} triples). Já tem python/bundle_for_oxen.py; precisa helper que produza ZIP no schema da fal. Submeter trainer com trigger <mapart isometric pixel art>. Output: v01.safetensors em URL pública.

1000 steps × $4/1k = $4 por iteração
1

Wire FalImageModel adapter (~1 dia)

Criar packages/models/src/fal.ts na linha do openai.ts:

export class FalImageModel implements ModelClient {
  readonly name: string;
  readonly modelId: string;
  readonly loraUrl?: string;
  private readonly apiKey: string;

  async generate(params: GenerateParams): Promise<GenerateResult> {
    // 1. Upload params.input (+ params.mask se houver) pro fal storage
    // 2. POST queue.fal.run/{modelId} com image_url, mask_url?, prompt,
    //    loras: this.loraUrl ? [{path: this.loraUrl, scale: 1.0}] : []
    // 3. Poll até resolver, baixar PNG, retornar
  }
}

Estender ModelName em types.ts:

export type ModelName =
  | 'stub'
  | 'nano-banana' | 'nano-banana-pro' | 'gemini-3.1-flash-image'
  | 'gpt-image-1' | 'gpt-image-1.5'
  | 'mapart-v01'           // nossa LoRA via fal qwen-image-edit-plus-lora
  | 'qwen-image-edit-2511' // Qwen base puro (fallback / benchmark)
  | 'z-image-turbo-inpaint'; // tier barato pra restyle leve

const FAL_MODELS = {

Riscos e tradeoffs

qualidade

LoRA v01 regredir fora do JP bbox

Training set é específico de área JP. Manter Qwen-Image-Edit-2511 puro como fallback no factory.

vendor

fal.ai cai → pipeline cai

Adapter abstrai endpoint. Backup Modal/Replicate quando crítico.

trigger

Trigger phrase "vazar"

<mapart isometric pixel art> pode contaminar prompts não-pixel. Validar com prompts adversariais no benchmark.

distillation

Z-Turbo soft em fine details

Distilled (8 NFEs) — output mais "soft" que Qwen-Edit. Rotear edits importantes pro Qwen mesmo sem máscara.

versionamento

LoRA artifact perder versão

Subir v01.safetensors pro R2/S3 próprio (não fal storage). Versionar /models/{version}.safetensors.

latência

fal queue latency variável

enable_sync_mode=true quando possível. Cache de tiles no worker-stylize.

cold start

Modal cold start mesmo com keep_warm

keep_warm=1 mínimo em prod. Aceitar 10-30s no primeiro request da janela.

migração

Qwen-Image-2.0 não casar com LoRA 20B

LoRA é por-arquitetura — re-treinar quando migrar pro 7B. Receita do trainer é reusável.
