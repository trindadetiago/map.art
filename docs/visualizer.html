map.art — visualizer

The shipped deep-zoom viewer — the realized build of what the isometric.nyc teardown sketched as the shape we'd likely adopt. One sentence: worker-stylize produces per-tile pixel-art → @mapart/export stitches them into one raster and slices a DZI/WebP pyramid → OpenSeadragon pans/zooms it with smoothing off → static tiles sit in S3/t3, streamed through a thin Next route with immutable cache + CORS.

Two halves, don't confuse them

build-time · offline

The export (@mapart/export)

Pure server-side. exportProjectDzi(projectId) reads a project's tiles, stitches the per-tile (x,y) stylized images into one giant raster, and slices a DZI/WebP pyramid into viz/{projectId}/ in storage. Runs from the CLI or a one-off Railway service — never in the request path.

runtime · the viewer

The viewer (apps/visualizer)

Next.js on :3220. One OpenSeadragon instance over a project's pre-built pyramid (/?project=<id>). At view time there's no scene and no camera — the isometric look is baked into the pixels, so this is a flat raster pan/zoom widget. This doc is mostly about how the two connect.

The stack

Next.js 15 (App Router) OpenSeadragon (tile viewer) sharp / libvips (dzsave) DZI / WebP (tile format) @mapart/storage (S3 / t3) Railway (export-runner)

Pipeline, end to end

  1. build · export

    Stitch the tiles, slice the pyramid

    exportProjectDzi downloads each present tile to a temp dir, then stitches in two passes: one full-width strip per grid row (a memory-mapped libvips .v), then the strips assembled into the pyramid via sharp's .tile({ layout: 'dz' }). Two passes cap concurrent inputs to dozens instead of thousands — compositing every tile at once OOM-kills a multi-gigapixel canvas. The grid's y is inverted (north on top). Everything uploads under one prefix:

    viz/{projectId}/
  metadata.json          # VizMetadata: dims, tileSize, format, grid, source
  tiles.dzi              # the DZI descriptor sharp emits (kept for debugging)
  tiles_files/
    0/0_0.webp           # lowest zoom level (1 tile)
    ...
    16/97_77.webp        # full-res 512px WebP tiles
  2. serve · next route

    A thin tile proxy (the Cloudflare-Worker analog)

    app/api/viz/[...path]/route.ts streams viz/<path> out of storage and stamps Cache-Control: public, max-age=31536000, immutable + CORS. No tile logic. It also smooths the opening burst with a process-wide semaphore, retries transient storage failures, and returns 503 (retryable) rather than 404 when a fetch is throttled — so a stampede of tile requests can't leave OpenSeadragon with permanent black gaps.

  3. client · openseadragon

    One viewer instance does the rest

    components/viewer.tsx mounts a single OSD instance over the pyramid, built from metadata.json. Pan/zoom, the built-in navigator minimap, and the pixel-art crispness settings all live here. Details below.

Inside the export — the load-bearing bits

memory

Two-pass strip stitch

Compositing ~2000 tile layers onto a ~2-gigapixel canvas in one shot gets OOM-killed (exit 137). Build per-row strips first (≤gridWidth inputs each), then assemble gridHeight strips — peak memory stays in the hundreds of MB regardless of project size.

memory

Download to disk, not RAM

Tiles are written to a temp dir and composited from file paths (lazy libvips reads), so we never hold thousands of decoded buffers resident. Fetches and uploads are bounded (16 inflight) — an unbounded Promise.all saturates the S3 pool and remote storage starts cancelling requests.

orientation

Row axis inverted

Grid y increases northward, but image rows run top→down. The stitch places the highest y on top so the map comes out the right way up; columns map straight across.

robustness

Probe, don't assume

The source tile pixel size is read from the first image rather than hard-coded (renders are 1024px, not 512). The pyramid tile size stays 512 — the OSD/DZI default — independent of the source.

Inside the viewer — the clever bits

gotcha

Own the tile URL

The tile source uses an explicit getTileUrl, not the legacy DZI { Image } descriptor. OSD's built-in DZI URL builder concatenates fileFormat + queryParams, and the minified prod bundle appends a literal undefined — every tile requested …_y.webp undefined and 404'd. It worked in dev (unminified) and only broke in production.

pixel art

Keep pixels crisp

imageSmoothingEnabled: false (no bilinear blur), maxZoomPixelRatio: 8 with nearest-neighbour over-zoom (inspect individual pixels without mush), smoothTileEdgesMinZoom: Infinity, plus image-rendering: pixelated on the canvas.

layout

Size the container explicitly

OSD forces position: relative inline on its element, which defeats inset: 0 sizing — the div collapses to height 0 and the canvas draws into 1px. The .viewer uses 100vw/100vh so it fills the viewport regardless.

free features

Minimap + fallbacks

The minimap is OSD's built-in navigator. The page also handles the no-pyramid-yet state (with the exact mapart export command to run) and a project picker when ?project is absent.

Running an export

The export is a build step, not a request. Two ways to run it:

  1. local · dev

    Against local MinIO

    pnpm mapart export dzi --project <id>    # --source stylized|rendered, --quality
  2. prod · railway

    Against t3 storage, from inside Railway

    Running the export against prod from a laptop stalls — t3 throttles/cancels requests over the public internet and the prod DB is private-only. So run it inside Railway:

    node scripts/export-on-railway.mjs <projectId> [stylized|rendered]

    This deploys a reusable, normally-idle export-runner service (internal DB + local-fast t3), runs the CLI, polls the new deployment's logs to completion, then goes idle (no compute billed). Re-running just redeploys it with a new project id.
