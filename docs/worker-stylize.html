map.art — worker-stylize

The third service in the pipeline. worker-render turns a map area into raw isometric renders; worker-stylize turns each rendered tile into seamless pixel-art by giving an image model the raw tile plus thin strips of its already-stylized neighbours, so the style flows continuously across tile borders. See the architecture for the full system; this page documents the stylize worker as built.

Where it sits

Every tile is a queue row. A tile lives in one phase at a time — render then stylize — and each worker claims rows with FOR UPDATE SKIP LOCKED. The stylize worker is a long-running apps/* service with no HTTP surface; coordination lives entirely in the tiles table. 

area → grid of tiles  ─┬─►  worker-render   ─►  render/{project}/{x}_{y}.png   (phase: render, status: done)
                       └─►  worker-stylize  ─►  stylize/{project}/{x}_{y}.png  (phase: stylize, status: done)

The per-tile pipeline

The consumer loop mirrors worker-render: claim one row, do the slow work outside any transaction, mark it done or retry, back off ~30s when the queue is empty. 

const tile = await claimNextStylize();              // promote render/done (neighbours rendered) or re-claim a failed stylize
if (!tile) { await idle(); continue; }          // empty queue → back off

const render    = await getStorage().get(tile.renderedImgPath);
const neighbors = await loadStylizedNeighbors(tile);  // tilesByIds(tile.neighbors), keep only those already stylized
const { composite, bbox } = await buildComposite(render, neighbors);
const { image } = await model.generate({ input: composite, prompt: STYLIZE_PROMPT });
const stylized = await extractStylized(image, bbox);
await getStorage().put(stylizeKey(tile), stylized);
await completeStylize(tile.id, stylizeKey(tile));   // any failure → failOrRetry(tile.id)

Algorithm A — the composite

The recipe is a faithful port of python/algorithm_playground.py. Each model call is a single 1024×1024 image: the centre is the raw render to stylize, each side that has an already-stylized N/S/E/W neighbour gets a thin strip cropped from that neighbour's adjacent edge, and a 1px red rectangle marks the region to fill — the convention the model is trained on.

The rules that make it seamless

  • Strips, not whole tiles. Each present stylized neighbour contributes a ~10% strip cropped from the edge adjacent to this tile, so the model extends an established style rather than inventing one.
  • Missing side → opposite doubles. A neighbour that is a grid edge — or simply not stylized yet — is treated as absent; the opposite side's strip doubles to keep the composite square without padding.
  • Diagonals fill corners only. Diagonal neighbours patch the composite's corner squares (falling back to extending an edge strip), but never reshape the rectangular red region.
  • Extract. After inference, the red-outlined region is cropped back out and resized to 1024² — that is the stored tile, and it becomes a neighbour strip for the next one.

Tiles are not stylized in an arbitrary order: claimNextStylize only promotes a tile whose neighbours have all rendered, which approximates the playground's expanding-radius walk ((0,0) → (0,1)(1,0) → …) so a tile tends to have stylized neighbours to anchor on. The composite uses whichever neighbours are already stylized at claim time and treats the rest as absent — a pure function of (render, stylized-neighbours).

Components

package · pure

@mapart/stylize

Server-only, sharp-based, no DB or network. buildComposite(render, neighbours, opts) → { composite, bbox } and extractStylized(output, bbox), plus TILE_SIZE, DEFAULT_CONTEXT_PCT, and STYLIZE_PROMPT. Unit-tested for geometry parity in isolation.

app · service

apps/worker-stylize

consumer.ts — startStylizeConsumer(model, log), the claim/compose/model/crop/store/complete loop with idle backoff and graceful stop. worker.ts — the entry that wires the model and handles SIGINT/SIGTERM.

models

ModelClient seam

The worker talks to the model only through generate({ input, prompt }) → { image }. StubImageModel echoes the composite back, so the whole pipeline runs with no GPU, key, or cost — the plumbing is exercised end to end and the crop step still runs on the real bbox.

db · read

tilesByIds

A tile stores its neighbours as a uuid[]. tilesByIds resolves those ids into rows so the worker can read each neighbour's x/y (to classify the direction) and stylizedImgPath (to load the strip). Read-only; the claim/complete SQL is unchanged.

The model: stub now, real next

The pipeline is decoupled from the model behind one interface, which lets the worker ship and be tested against a stub before a real inference backend exists.

StubImageModel in use Echoes the input. Default for tests, CI, and local pnpm dev — deterministic, free, no dependencies.
Oxen LoRA (v02) planned The fine-tuned model the red-box recipe was trained on, served at hub.oxen.ai/api/images/edit. Lands as a new ModelClient behind the same seam, selected by env — no worker changes.

Running it

# under the dev TUI — worker-stylize gets its own tab
pnpm dev
# or standalone
pnpm dev:worker-stylize

# tests (worker + db suites need the local Postgres up + migrated)
pnpm --filter @mapart/stylize test          # pure geometry parity, no DB
pnpm --filter @mapart/worker-stylize test   # end-to-end against the queue

Storage keys follow the render convention: stylized tiles land at stylize/{projectId}/{x}_{y}.png via getStorage() (local data/ or S3/MinIO, per STORAGE_BACKEND). Failures bump the per-phase retry budget; the 4th failure is terminal (error).
